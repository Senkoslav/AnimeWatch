# 05. Видеоконвейер

Самая рискованная часть проекта. Читай целиком перед любой задачей, где есть
слово «видео».

## Исходные данные

- Мастер серии ~3.5 ГБ на 24 минуты (≈19–20 Мбит/с).
- Лежит в приватном телеграм-канале, залит как файл с Premium-аккаунта.
- Скачивать такое зрителю нельзя: один просмотр — 3.5 ГБ трафика и вечная
  буферизация на телефоне.

Первое, что делается на старте: `ffprobe` по нескольким файлам. Если это апскейл
1080p, дорожка 2160p не собирается вообще — она вчетверо дороже и не добавляет
деталей. Результат проверки записать сюда.

## Поток

```
1. Редактор в админке создаёт Episode и указывает ссылку на пост в канале
2. Создаётся IngestJob { tgChatId, tgMessageId, status: PENDING }
3. Воркер берёт задачу:
   DOWNLOADING → тянет мастер по MTProto чанками во временный файл
   UPLOADING   → создаёт видео в Bunny (POST /library/{id}/videos),
                 заливает через TUS с резюмом
   ENCODING    → ждёт вебхук от Bunny
4. Вебхук /api/webhooks/bunny со статусом готовности:
   создаёт Source { type: HLS, url: <videoId>, isDefault: true },
   заполняет Episode.duration и thumbUrl, ставит IngestJob.status = READY
5. Редактор проставляет publishedAt — серия появляется на сайте
```

Пока `status != READY`, серия может быть опубликована с временным источником
`type: TELEGRAM` (виджет поста). Схема `Source[]` это допускает, переключение на
HLS произойдёт автоматически, когда появится источник с большим приоритетом.

## Правила телеграм-клиента

- MTProto (GramJS), **не** Bot API: боту доступны файлы только до 20 МБ.
- Отдельный аккаунт на отдельную симку, с Premium, админ канала. Личный аккаунт
  участника студии в продакшн не тащим: это доступ ко всей его переписке и риск
  потерять аккаунт по флуд-бану.
- Сессия хранится как секрет воркера, в репозиторий не попадает никогда.
- Скачивание чанками; параллелить осторожно. `FLOOD_WAIT_x` — не ошибка, а
  указание подождать x секунд: ловим, спим, продолжаем.
- Одна задача за раз. Конкурентность очереди = 1, пока не измерим реальные лимиты.
- Ретраи с экспоненциальной паузой, максимум 3 попытки, потом `FAILED` с текстом
  ошибки в БД и уведомлением в служебный чат.

## Bunny Stream

- Кодирование включено на стороне библиотеки, отдельно не тарифицируется.
- Лестница на старте: **480p / 720p / 1080p**. 2160p включается точечно и только
  для тайтлов, где исходник действительно 4K.
- Загрузка — TUS (резюмируемая). Для 3.5 ГБ обычный POST не годится: обрыв
  посередине означает заново.
- Вебхук обязан проверять подпись. Необработанный вебхук без проверки — это
  открытый эндпоинт, которым можно подсунуть чужой videoId.
- Включить сразу: hotlink protection, список разрешённых доменов, token
  authentication. Не «после запуска».

## Воспроизведение

- Клиент запрашивает `/api/playback/[episodeId]`, сервер проверяет, что серия
  опубликована и тайтл не скрыт, и возвращает подписанный URL плейлиста с
  ограниченным временем жизни.
- Срок жизни токена должен покрывать длительность серии с запасом — иначе плеер
  оборвётся на середине просмотра. Это самая частая ошибка в такой связке.
- Плеер — Vidstack, провайдер HLS (hls.js под капотом), кастомный UI на
  Tailwind-компонентах, не Default Layout.
- Известная засада: в App Router при клиентской навигации `TimeSlider.Value`
  может падать в проде. Собираем значение времени сами через `useMediaState`.
- Качество по умолчанию — авто. Ручной выбор сохраняем в localStorage: это
  настройка устройства, ей в БД делать нечего.

## Деньги

Считается как «средний вес просмотра × число просмотров». После перехода на
лестницу зритель тянет примерно 0.5–1 ГБ вместо 3.5 — это и есть главная
экономия. Хранение лестницы — порядка полутора-двух гигабайт на серию.

Перед запуском: собрать текущие тарифы Bunny и посчитать три сценария —
1 000 / 5 000 / 20 000 просмотров в месяц. Цифры показать студии до того, как
включать 2160p.

## Что должно быть в мониторинге с первого дня

- Количество задач в статусе `FAILED` за сутки
- Время от создания задачи до `READY`
- Суточный трафик Bunny (алерт при резком росте — обычно это хотлинк)
