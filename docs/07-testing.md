# 07. Тестирование

Тесты здесь не ради покрытия. Они закрывают места, где поломка тихая и дорогая:
приватность черновиков и скрытых тайтлов, подделка сессии, адрес чужого фрейма,
форма правообладателя, лимиты запросов.

## Уровни

**Vitest** — чистая логика: маппинг Shikimori → `Title`, проверка домена
фрейма (`embedSrc`), разбор поискового запроса, схема формы обращения, утилиты
форматирования. Сеть и БД замоканы, тест идёт миллисекунды.

**Vitest + тестовая БД** — запросы Prisma и server actions. `pnpm test:db`,
Vitest-проект `db`: отдельная база `animewatch_test` (локальный Postgres или
service-контейнер в CI, URL в `TEST_DATABASE_URL`, имя обязано кончаться на
`_test`), `prisma migrate deploy` перед прогоном, `TRUNCATE` всех таблиц перед
каждым тестом, файлы по очереди. Не транзакция с откатом: код под тестом сам
открывает транзакции Prisma. Хелперы публичной выдачи проверяются на базе
напрямую, а не только через запросы поверх них: запрос может сам по себе
спрятать сломанный фильтр.

**Playwright** — пользовательские сценарии целиком. Проекты: `chromium-desktop`
и `mobile-chrome` (Pixel 7). Мобильный прогон обязателен, это основной трафик.
Фрейм поставщика в e2e не загружается по-настоящему: запрос к его домену
перехватывается, проверяется `src` фрейма и состояние страницы. В живой Kodik
тесты не ходят никогда.

Окружение e2e (`playwright.config.ts`): у тестового сервера тестовые ключи
Google — вход включён, но настоящий Google не вызывается никогда; Redis не
подключён — лимиты пропускают запросы. Вошедший зритель — `signInAs()` из
`tests/e2e/db.ts`: пользователь и сессия пишутся в локальную базу, куки — в
контекст браузера. Тестовые пользователи с `googleId` на `e2e-` удаляются в
`global-setup.ts` перед каждым прогоном.

Две ловушки, на которых тесты уже врали:
- Клик Playwright не ловит обрезку контейнером с `overflow-hidden`: перед
  кликом он прокручивает такой контейнер программно, а человек этого не может.
  Обрезку проверять геометрией (низ элемента против низа обрезающих предков).
- `getByLabel` ищет по подстроке: закрытое окно поиска с полем «Название аниме»
  лежит в DOM на каждой странице. Подписи полей искать с `exact: true`.

## Что тестируем обязательно

Приватность и доступ:
- черновик (`publishedAt = null`) не виден анониму нигде: ни на странице тайтла,
  ни в каталоге, ни в поиске, ни в sitemap
- `Title.status = HIDDEN` убирает тайтл и все его серии из публичной выдачи
- условия публичности в сыром SQL поиска не расходятся с `publicTitleWhere()`

Фрейм плеера:
- адрес с чужого домена во фрейм не попадает (`embedSrc`)
- серия без источника показывает состояние «не подключён», а не пустой экран
  и не 404

Форма обращения (/dmca):
- обращение попадает в базу до попытки уведомления
- падение канала уведомления не теряет обращение и не ломает подтверждение
- шестое обращение с того же адреса за час отклоняется
- заполненная ловушка не создаёт записи

Импорт:
- повторный импорт того же `shikimoriId` не плодит дубли
- ответ Shikimori разбирается zod: мусор в поле не роняет импорт целиком

Вход и сессии (`lib/auth/`):
- выдуманный токен, id пользователя вместо токена, хеш вместо токена,
  просроченная и чужая сессия — никто
- после выхода сохранённая кука ничего не открывает
- кука сессии `HttpOnly; Secure; SameSite=Lax`; адрес возврата — только свой путь
- `id_token` с чужим `aud`, чужим издателем, просроченный или с неподтверждённым
  e-mail — отказ; в собранном клиентском бандле нет ни секрета, ни его имени

Отметки, оценки, профиль:
- action без сессии — «войдите», с мусором — отказ до базы
- черновик и скрытый тайтл не отмечаются и не попадают в профиль
- счётчики профиля сходятся с содержимым `Bookmark`
- «смена устройства»: второй контекст браузера с другой сессией видит то же

Лимиты и поиск:
- счётчик пропускает до предела и отсекает сверх; зависший Redis — таймаут, а
  не вечное ожидание; нет Redis — запросы проходят (fail-open)
- поиск в окне: клавиатура целиком, фокус возвращается туда, откуда открыли,
  без JS лупа ведёт на `/search`

## Доступность

`@axe-core/playwright` прогоняется на главной, каталоге, странице тайтла,
поиске, странице просмотра и `/dmca`. Нарушения уровня `critical` и `serious`
роняют сборку. Отдельно проверяется, что фокус виден на всех интерактивных
элементах: содержимое фрейма — зона поставщика, всё остальное наша.

## Производительность

Бюджеты: LCP < 2.5 с, CLS < 0.1 на мобильном, вес JS на первой загрузке
< 200 КБ gzip. Мерить по Vercel Speed Insights — метрики настоящих зрителей по
страницам и устройствам. Lighthouse на localhost для этого не годится: в режиме
`simulate` он даёт 3.3 с независимо от вёрстки. Lighthouse CI в пайплайне пока
не настроен.

## Чего не тестируем

Вёрстку попиксельно. Скриншотные тесты на верстающемся проекте дают ложные
падения каждый день и обучают игнорировать красный CI. Визуальное качество
проверяется скиллом `/ui-review` вручную перед сдачей фазы.

Не пишем тесты на геттеры, на то, что Prisma работает, и на верстку статичных
страниц.

## Данные для тестов

Фабрики в `tests/factories`, не общий seed-дамп (e2e пока идут на dev-базе
после `pnpm db:seed`). Каждый тест создаёт ровно то,
что ему нужно. Фикстуры внешних ответов (Shikimori, Kodik) лежат в
`tests/fixtures` и обновляются вручную при изменении контрактов.

## CI

Пайплайна в репозитории пока нет (`.github/workflows` пуст): проверки гоняются
локально перед каждым слиянием — `pnpm verify`, `pnpm build`, `pnpm test:e2e`.
Когда появится CI, порядок тот же: `typecheck → lint → test:unit → test:db →
build → test:e2e`, и ветка не мержится с красным пайплайном. Сборку каждой ветки
уже проверяет превью Vercel со своей веткой базы Neon.

Флаки-тест либо чинится в тот же день, либо удаляется — «иногда падает» хуже,
чем «нет теста». Разовое падение из-за того, что дев-сервер тестов не успел
подняться под нагрузкой, флаки не считается: повтор отдельно проходит.
