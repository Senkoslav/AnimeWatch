# 02. Архитектура

## Топология

```
Телеграм-канал (мастера 3.5 ГБ)
        │  MTProto, отдельный аккаунт-воркер
        ▼
  Worker (VPS, Node + BullMQ)  ──►  Bunny Stream  ──►  Bunny CDN (HLS)
        │                                │                   │
        │ статус задачи                  │ webhook            │ .m3u8 + сегменты
        ▼                                ▼                   ▼
   PostgreSQL  ◄────────────────  Next.js (Vercel)  ────►  Браузер зрителя
```

Next.js никогда не стоит на пути видеотрафика. Он отдаёт HTML и подписанный URL
плейлиста, дальше браузер общается с CDN напрямую.

## Компоненты

**Web (Vercel).** Next.js App Router, SSR/ISR для публичных страниц, админка —
динамическая. Vercel запрещает раздачу видео через свою сеть, поэтому любой
код, который проксирует видеопоток, — ошибка проектирования.

**База (Neon/Supabase, Postgres).** Prisma. Connection pooling обязателен:
serverless-функции открывают соединения агрессивно.

**Воркер (VPS, Hetzner/Aeza).** Отдельный репозиторий-пакет в монорепо,
собственный процесс. Очередь на BullMQ поверх Redis. Делает ровно одно:
забирает мастер из телеграма и отдаёт в Bunny, обновляя статус в БД.

**Bunny Stream.** Транскодинг в лестницу качеств, хранение, раздача HLS,
токен-аутентификация, вебхуки о готовности. Кодирование не тарифицируется
отдельно, платим за хранение и трафик — актуальные цифры проверять на сайте.

## Маршруты

```
/                         главная: свежие серии
/catalog                  каталог с фильтрами (searchParams = состояние)
/anime/[slug]             страница тайтла
/anime/[slug]/[episode]   просмотр
/team                     команда и роли
/news, /news/[slug]       новости
/search                   поиск
/me                       закладки и «продолжить»
/admin/*                  админка (роль ADMIN | EDITOR)
/dmca, /terms, /privacy   обязательные страницы

/api/webhooks/bunny       вебхук о готовности видео
/api/auth/telegram        проверка подписи Telegram Login
/api/playback/[episodeId] выдача подписанного URL плейлиста
/api/progress             сохранение позиции (батчем, не каждую секунду)
```

## Кеширование

- Каталог и карточки тайтлов — ISR, `revalidate: 300`, плюс точечный
  `revalidateTag('title:<id>')` из админки после правки.
- Главная — `revalidate: 60`.
- Страница просмотра — динамическая: подписанный URL живёт недолго.
- `/me`, админка — `no-store`.
- Теги: `titles`, `title:<id>`, `episodes:<titleId>`, `news`.

## Безопасность

- Ссылки на плейлист подписываются на сервере и живут ограниченное время.
  Срок должен покрывать длину серии с запасом, иначе плеер отвалится на середине.
- Hotlink protection и разрешённые домены в Bunny включаются сразу, не «потом».
  Иначе каталог утащит чужой агрегатор, а трафик оплатим мы.
- Telegram Login проверяется по HMAC от токена бота, с проверкой `auth_date`.
  Данные виджета без проверки подписи — не авторизация.
- Роли: `USER | EDITOR | ADMIN`. Проверка роли в каждом server action первым
  делом, не в UI.
- Rate limit на `/api/playback` и поиск.
- Секреты Bunny и сессия телеграм-аккаунта живут только на воркере и на сервере.

## Решения и их причины

| Решение | Почему так, а не иначе |
|---|---|
| Bunny Stream, не свой ffmpeg | 4K-энкод на CPU — часы на серию; нужен GPU и обслуживание |
| Bunny, не Cloudflare Stream | у CF тарификация по минутам, на нашем объёме выходит дороже |
| Телеграм как архив | бесплатно и уже используется студией; но только как холодное хранилище |
| Vidstack, не video.js | headless-компоненты, нормальный React/RSC-путь, свой UI без борьбы с темами |
| Postgres, не MongoDB | связи тайтл↔серия↔роль↔актёр реляционные по природе |
| Telegram Login, не email | вся аудитория и так в телеграме; email-регистрация — лишний барьер |
